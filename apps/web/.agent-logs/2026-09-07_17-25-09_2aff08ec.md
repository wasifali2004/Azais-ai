## Setup decision: `next-intl`

Confirmed via Next's own bundled docs: App Router has **no built-in i18n config** — that only ever existed for the Pages Router. Real path-based routing (`/en`, `/es`, etc.) requires every route to live under an `app/[locale]/...` segment regardless of approach, so there's no "simpler built-in" option to fall back to here.

Going with **next-intl** (v4.14.2, declares support for Next `^16.0.0`) over hand-rolling it, because:
- Next's own docs' hand-rolled i18n example is Server-Component-only ("this code will only run on the server") — but this app is heavily client-component-driven (framer-motion, forms, `useState`-based interactivity everywhere), and next-intl's `useTranslations()` + `NextIntlClientProvider` is the mature, tested way to get translated strings into Client Components. Reinventing that myself would be redoing solved work.
- It's Next's own top pick in that same docs page's library list.
- I confirmed empirically (not from memory) that `middleware.ts` still works under this exact Next 16.3.4 install — I tested it live against the other session's running dev server, since Next 16 renamed Middleware→Proxy and I didn't want to assume backward compatibility. It works, so next-intl's standard `middleware.ts` setup needs no adjustment.
